## Pre-flight (all gates)

Before any gate:

1. Run `git branch --show-current` — must be the authorized gate branch (or `main` if post-merge).
2. Run `git status --short` — working tree must be clean before apply.
3. Run `node scripts/google-calendar-source-validate.mjs` — source records must be valid.
4. Confirm `docs/project-control/external-sync-map.local.json` is gitignored: `git check-ignore -v docs/project-control/external-sync-map.local.json`.
5. Confirm canonical credential paths are gitignored:
   ```
   git check-ignore -v docs/project-control/google-calendar-credentials.local.json
   git check-ignore -v docs/project-control/google-calendar-token.local.json
   ```

## Gate 2B — Live Calendar Dry-Run (real Google Calendar, read-only)

**Authorization required:** Coordinator must authorize Gate 2B separately.

**Prerequisites:**
1. Gate 2A is complete.
2. `googleapis` npm package installed in `scripts/` (Gate 2C — already done if Gate 2C is merged):
   ```
   npm --prefix scripts ls googleapis   # should show googleapis@173.0.0
   ```
3. Google Calendar API credentials configured at the canonical paths:
   - `docs/project-control/google-calendar-credentials.local.json` — credential file (gitignored).
   - `docs/project-control/google-calendar-token.local.json` — token file (gitignored, generated by OAuth bootstrap).
   - See `google-calendar-credentials.example.md` for setup instructions.
4. OAuth token generated via:
   ```
   node scripts/google-calendar-auth-bootstrap.mjs --init-oauth
   ```
   (Requires explicit Coordinator authorization — opens browser OAuth flow, writes token locally.)
5. Coordinator has added `AI_OS_ID:` markers to existing Google Calendar events (see adoption guide in `google-calendar-sync-policy.md`) — OR — accepts ADOPTION_REQUIRED classifications and plans to resolve them before Gate 3.

**Steps:**

1. Run pre-flight checks.
2. Check auth readiness (existence check only, no contents read):
   ```
   node scripts/google-calendar-auth-bootstrap.mjs --auth-status
   ```
   Expected: `STATUS: READY`
3. Run source validation.
4. Run live dry-run (requires Coordinator authorization):
   ```
   node scripts/google-calendar-sync-dry-run.mjs --live-readonly
   ```
5. Review classified delta output:
   - `NO_OP`: event matches source record — no action needed.
   - `CREATE`: event not found — will be created in Gate 3.
   - `UPDATE`: event found but non-time fields differ — will be updated in Gate 3.
   - `REMOTE_DRIFT`: event found but time/date differs (external edit detected) — Coordinator must review.
   - `ADOPTION_REQUIRED`: existing event found by title/date, no AI_OS_ID marker — add marker before Gate 3.
   - `DUPLICATE_DETECTED`: two events match same AI_OS_ID — Coordinator must resolve before Gate 3.
   - `POSSIBLE_DUPLICATE`: weak title match, no marker — advisory only, does not block Gate 3.
   - `NEEDS_MANUAL_REVIEW`: multiple exact matches, no marker — Coordinator must pick the right event.
   - `MAPPED_EVENT_MISSING_REMOTELY`: local sync map entry exists but event is gone — investigate.
   - `DELETE_CANCEL_CANDIDATE`: managed event with no source record — report only, separate approval needed.
   - `MISSING_LOCAL_MAPPING`: managed event found but no local sync map entry — advisory flag on NO_OP/UPDATE.
5. Save dry-run artifact to `local-sync-reports/google-calendar-dry-run-<timestamp>.json`.
6. Coordinator reviews and approves the delta.
7. Record Gate 2B result in `google-calendar-sync-log.md`.
8. If credentials missing: record `GATE_2B_BLOCKED: LIVE_READINESS_BLOCKED_CREDENTIALS_MISSING` in sync log.
9. If `googleapis` missing: record `GATE_2B_BLOCKED: LIVE_READINESS_BLOCKED_DEPENDENCY_MISSING` in sync log.

**Gate 2B does not mutate any calendar event.**

**Gate 2 does not mutate any calendar event.**

## Gate 3 — Live Calendar Apply

**Authorization required:** Coordinator must provide explicit "proceed with apply" instruction.

**Prerequisites:**
1. Gate 2 dry-run completed and approved.
2. Dry-run artifact saved at a known path.
3. No unresolved `DUPLICATE_DETECTED` or `ADOPTION_REQUIRED` items.
4. Credentials still valid (re-run dry-run if more than 24 hours have passed since Gate 2).

**Steps:**

1. Run pre-flight checks.
2. Run apply:
   ```
   node scripts/google-calendar-sync-apply.mjs \
     --apply \
     --confirm-live-calendar-apply \
     --approved-dry-run local-sync-reports/google-calendar-dry-run-<timestamp>.json
   ```
   The `--confirm-live-calendar-apply` flag is the runtime Gate 3 confirmation — no source code editing required.
3. Apply creates and updates events only. Delete/cancel requires separate step (see below).
4. After apply: run post-apply dry-run to verify:
   ```
   node scripts/google-calendar-sync-dry-run.mjs --live
   ```
   All events should classify as `NO_OP`.
5. Verify events in Google Calendar UI — confirm descriptions include `AI_OS_ID:` markers.
6. Review `external-sync-map.local.json` locally — confirm Google Calendar event IDs are populated.
7. Record Gate 3 result in `google-calendar-sync-log.md`.
8. Propose state-sync commit for `google-calendar-sync-log.md`; await Coordinator authorization.
9. v1.6 is complete (or record credential/platform blocker).

**Delete / cancel procedure (separate approval required):**

If the dry-run identified `DELETE_CANCEL_CANDIDATE` items:

1. Coordinator approves each deletion individually.
2. Run per-item delete:
   ```
   node scripts/google-calendar-sync-apply.mjs \
     --apply --confirm-live-calendar-apply \
     --approved-dry-run <path> --delete --os-id <os_id>
   ```
3. Log each deletion in `google-calendar-sync-log.md` with approval reference.

## Credential blocker handling

If Google Calendar API credentials are not available:

1. Record the blocker in `google-calendar-sync-log.md`:
   ```
   ## YYYY-MM-DD — Gate N blocked: credentials missing
   - Status: BLOCKED
   - Reason: Google Calendar API credentials not configured locally
   - Unblock path: follow docs/project-control/google-calendar-credentials.example.md
   ```
2. v1.6 is still considered complete when a documented blocker is recorded with a clear unblock path.
3. Run Gate 2 and Gate 3 when credentials become available.
